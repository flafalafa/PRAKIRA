# T-704: Status Banjir & Prediksi API Enterprise (Enterprise Flood Status & Prediction API)

## Ringkasan
Berhasil mengimplementasikan **Enterprise Flood Status & Prediction API**. API ini adalah denyut nadi dari Flood Guardian. Di sinilah aplikasi seluler warga menarik kesimpulan terkini ("Apakah rumah saya aman?") dan aplikasi *dashboard* BPBD membaca rincian analitiknya ("Mengapa level air naik?").

## Keputusan Arsitektur
1. **Pengawasan Ketat (Strict Segregation)**: Sesuai pedoman arsitektur, API Layer ini secara mutlak DILARANG MENGHITUNG. Semua nilai risiko, level bahaya, waktu tiba air (ETA), dan rekomendasi evakuasi sepenuhnya diambil dari Entitas `Prediction` yang dihasilkan oleh *Decision Engine* di Sprint 4. Jika *Decision Engine* salah, API akan mengembalikan kesalahan tersebut secara jujur. Tidak ada "perbaikan data" (data tampering) di level API.
2. **Abstraksi Penjelasan (Explainability Contract)**: Sistem memetakan kamus internal `explanation` (yang kompleks) menjadi `PredictionExplanation` DTO yang stabil. Parameter seperti `primary_risk_factors` dan `reason_summary` memungkinkan antarmuka (*Frontend*) menampilkan "Mengapa" prediksi ini dibuat.
3. **Pemisahan Jalur Status vs Prediksi**:
    - `GET /areas/{id}/flood-status`: Mengembalikan *Snapshot* (potret kilat) ringan yang dirancang untuk layar beranda utama (*Home Screen*) aplikasi HP warga. Memuat skor, level, dan ETA.
    - `GET /predictions/{id}`: Mengembalikan data raksasa (termasuk penjelasan mesin, data radar mentah pendukung, dsb) yang dirancang untuk layar detail atau untuk analisis pakar bendungan.
4. **Paginasi Historis**: Rute histori prediksi mematuhi kontrak `PaginatedResponse` (T-701) dengan dukungan *query parameter* `from_date` dan `to_date` agar peramban tidak *crash* jika memuat data historis 10 tahun.
5. **Kepatuhan Keamanan Otomatis**: Layaknya T-703, seluruh rute ini dibungkus menggunakan `Depends(get_current_user)`. Seseorang harus memegang Kunci API (API Key) atau Token JWT yang diakui untuk melihat data ini.

## Batasan yang Diketahui
- Untuk keperluan *stubbing* dan *mocking*, `PredictionApplicationService` saat ini meniru implementasi *database* filtering. Kelak ketika integrasi SQLAlchemy sepenuhnya terajut, pencarian rentang tanggal (`from_date` & `to_date`) harus dijalankan di lapisan `WHERE` SQL, bukan di memori Python.
- Caching `GET /flood-status` (yang berpotensi dipanggil jutaan kali per detik saat hujan deras) belum diimplementasikan dengan Redis karena spesifikasi PRD secara eksplisit melarang implementasi Redis pada fase ini.

## Peningkatan Kedepan
- **Redis Caching**: Menyimpan respons `/flood-status` di Redis dengan usia hidup (*Time-to-Live* / TTL) 1-2 menit. Hal ini akan menyelamatkan nyawa *database* Postgres utama dari amukan *query* jutaan warga Jabodetabek secara bersamaan saat badai.
