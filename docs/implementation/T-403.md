# T-403: Pengumpul Data OpenWeather (OpenWeather Collector)

## Ringkasan
Berhasil mengimplementasikan Modul Kolektor untuk OpenWeather. Sama halnya dengan kolektor BMKG (T-402), modul ini mewarisi secara penuh disiplin arsitektur *Enterprise Collector Foundation* (T-401). Kehadiran kolektor OpenWeather sangat krusial bagi sistem *Flood Guardian* karena berfungsi sebagai sumber data sekunder (cadangan) yang menjamin keandalan sistem (*redundancy*). Kelak jika server BMKG sedang tumbang (down) atau data lokal terputus, sistem akan mengandalkan OpenWeather untuk memastikan mesin prediksi banjir tetap menyala dan masyarakat tetap terlindungi.

## Keputusan Arsitektur
1. **Otentikasi Aman (Secure Authentication)**: Berbeda dengan BMKG yang bersifat terbuka, OpenWeather menuntut *API Key*. Kolektor ini memastikan kunci rahasia (*API Key*) dibaca secara rahasia dari variabel lingkungan (`settings.py`) dan tidak di-*hardcode*. 
2. **Backoff Eksponensial (Exponential Backoff)**: Mengingat OpenWeather memiliki batas (*rate limit*) permintaan harian yang ketat (terutama untuk akun gratis), modul klien jaringan telah dipersenjatai dengan mekanisme Jeda Berlipat Ganda (*Exponential Backoff*). Jika permintaan gagal karena *Rate Limit* (Error 429), ia akan tidur (*sleep*) lebih lama sebelum mencoba lagi (misalnya tunggu 2 detik, lalu 4 detik, lalu 8 detik).
3. **Optimasi Titik Panggil (*OneCall API Optimization*)**: Di dalam fungsi `fetch()`, sistem dirancang untuk menembak titik henti (endpoint) `OneCall API`. Pendekatan ini sangat cerdas dan efisien karena hanya dengan satu kali pemanggilan HTTP saja (menghemat kuota API), kita sudah memanen data cuaca saat ini, cuaca per-jam, prediksi harian, hingga peringatan bahaya sekaligus.
4. **Strategi Pemetaan Cuaca (*Normalization Map*)**: *JSON* raksasa dari OpenWeather dibedah oleh `OpenWeatherParser` lalu dialihkan ke `OpenWeatherNormalizer`. Normalisasi sangat rapi, contohnya, data hujan OpenWeather yang tersembunyi jauh di properti `rain['1h']` ditarik keluar dengan aman dan disatukan menjadi nilai properti `"rainfall"` baku.

## Siklus Request & Normalisasi
1. **Connect**: Klien *httpx async* dibuka, mengecek *timeout* dan kunci otentikasi.
2. **Fetch**: Memanggil *OneCall API* dengan koordinat Lintang (Lat) dan Bujur (Lon). Raw Payload berformat JSON pun diraih.
3. **Parse**: Modul pembelah (Parser) membaca JSON mentah tersebut dengan memilah secara hati-hati properti wajib (`current`, `hourly`) serta menangani gracefully apabila properti prediksi absen (hilang).
4. **Normalize**: Parameter-parameter internasional khas cuaca seperti suhu, tutupan awan (`clouds`), jarak pandang (`visibility`), dikonversi menjadi zona waktu *UTC datetime* yang modern dan direkatkan ke dalam wadah `NormalizedData.time_series` dengan ID yang unik per koordinat spasial (`ow_loc_lat_lon`).

## Peningkatan Kedepan
- **Penggabungan Data (*Data Fusion*)**: Nanti di Sprint ke-5 atau ke-6, akan ada sebuah Layanan (*Fusion Service*) yang berdiri di tengah-tengah. Ia akan menyedot `NormalizedData` dari Kolektor BMKG dan `NormalizedData` dari Kolektor OpenWeather, membandingkan akurasinya, mencari titik tengah curah hujan, dan akhirnya menciptakan 1 (satu) entitas `Rainfall` emas nan absolut (Master Fakta Lapangan) sebagai bahan baku kalkulasi bahaya sungai.
