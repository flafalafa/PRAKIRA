# T-707: Lapisan Perlindungan API & Rate Limiting (Enterprise API Rate Limiting & Protection)

## Ringkasan
Berhasil mengimplementasikan **Enterprise API Rate Limiting & Protection Layer**. Modul ini adalah "Sabuk Pengaman" utama bagi *backend* Flood Guardian. Dengan implementasi ini, server kita tidak akan tumbang akibat *traffic spike* mendadak (ratusan ribu warga membuka aplikasi bersamaan saat banjir), serangan DDoS amatir, atau kesalahan program *looping* tanpa henti dari sisi klien (*Client-side bug*).

## Keputusan Arsitektur
1. **Pemisahan Logika (*Middleware Level*)**: Logika pembatasan (Rate Limit) tidak diselipkan secara manual satu per satu di dalam fungsi *Router*. Ia berdiri tegak di gerbang depan aplikasi (menggunakan `BaseHTTPMiddleware` FastAPI). Sebelum perintaan menyentuh *Controller/Router*, kelayakannya sudah disortir.
2. **Algoritma Token Bucket**: Saya memilih *Token Bucket* dibandingkan *Sliding Window Log* karena `Token Bucket` mengkonsumsi memori jauh lebih rendah (hanya menyimpan angka integer token dan *timestamp* terakhir, bukan larik *array* waktu), namun tetap mengizinkan semburan trafik mendadak (*Burst Traffic*) yang lazim terjadi di aplikasi seluler saat menerima Push Notification.
3. **Resolusi Identitas Cerdas (*Smart Key Resolution*)**: Jika pengguna sudah Login (via T-702 Security Context), maka kuotanya dihitung berdasarkan *User ID* murni (`auth:123`). Jika pengguna anonim (belum login), maka kuota dihitung dari IP Address asalnya (`anon:192.168.1.1`).
4. **Kebijakan Harga Khusus (*Cost-Based Policy*)**:
   - `GET /flood-status` (Super ringan) diberikan limit yang sangat dermawan (misal 300 request/menit).
   - `GET /predictions` (Super berat / Historis) langsung dicekik ke limit yang sangat pelit (misal 30 request/menit) untuk mencegah *database scanning* yang memakan CPU.
5. **Fail-Open Strategy**: Sesuai mandat SDS, jika di masa depan *server* Rate Limiter meledak/rusak, sistem memiliki konfigurasi darurat `fail_open=True`. Artinya perlindungan akan dimatikan otomatis dan arus diizinkan masuk, memastikan notifikasi darurat kebencanaan tetap dapat diakses publik!

## Integrasi Kontrak API (T-706)
Respons perlindungan dikemas utuh mematuhi standar SDS sebelumnya, mengembalikan HTTP 429 dan HTTP 413, menggunakan amplop `ApiError`, lengkap dengan `X-RateLimit-Limit`, `X-RateLimit-Remaining`, dan Header `Retry-After`.

## Strategi Migrasi ke Redis di Masa Depan
Implementasi MVP saat ini menggunakan `InMemoryTokenBucketLimiter` yang disimpan di RAM Python. Ini bekerja sangat baik untuk aplikasi dengan satu *container* (*Single Node*).
Di masa depan, jika Flood Guardian dijalankan di dalam kluster Kubernetes (Banyak *container*), kita hanya perlu membuat file baru `RedisLimiter(RateLimiterStrategy)` dan menukarnya di dalam `middleware.py`. *Zero-downtime* dan nol perubahan di level *Router* atau *Domain*.
