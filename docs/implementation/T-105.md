# T-105: Enterprise Error Management System

## Summary
Successfully implemented a robust, centralized enterprise error management system. This ensures all errors returned by the PRAKIRA backend conform to a strictly typed, uniform JSON response. This simplifies frontend and mobile app handling while preventing sensitive server data from leaking in production environments.

## Architecture Decisions
1. **Centralized Hierarchy (`AppException`)**: Implemented a base exception class mapping directly to standard HTTP status codes and specific internal error codes (`RESOURCE_NOT_FOUND`, `RATE_LIMITED`). Business components will only throw subclasses of `AppException`.
2. **Environment-Aware Global Handler**: In development mode, unhandled 500 exceptions output full `stack_trace` payloads directly in the JSON response to accelerate debugging. In non-development modes, the stack trace is entirely stripped out and replaced with a generic "unexpected internal server error" message.
3. **Pydantic Validation Interceptor**: Intercepted FastAPI's built-in `RequestValidationError` which originally returns a non-standard JSON list. Rewrote it to inject into the `ErrorResponse` model, placing the exact missing fields within the `details` array and setting `code = VALIDATION_ERROR`.

## Known Limitations
- The system currently maps HTTP errors generically (e.g. `HTTP_ERROR` for standard 405 Method Not Allowed). Future versions might want to build specific interceptors if more granular metric tracking on these 4xx errors is needed.

## Future Improvements
- **Internationalization (i18n)**: Tie exception messages to a translation dictionary (Bahasa Indonesia) depending on the incoming `Accept-Language` header for client-facing validation errors.
