# T-204: Enterprise Base Entity Framework

## Summary
Successfully implemented the foundational `BaseEntity` framework and reusable declarative Mixins for Flood Guardian. This architecture ensures that all future business entities (e.g. User, Area, River, Prediction) will uniformly inherit standard metadata, optimistic locking, UUID indexing, and soft-deletion rules without duplicating code.

## Architecture Decisions
1. **Separation of Concerns (Mixins)**: Features are heavily decoupled into independent mixin classes (`UUIDIdentifierMixin`, `TimestampMixin`, `AuditMixin`, `SoftDeleteMixin`, `VersioningMixin`). This allows flexibility. For instance, a temporary Cache entity might only need UUID and Timestamps, while a Financial Transaction entity might need Full Audit and Versioning.
2. **Standard Aggregations**: Created `StandardEntityMixin` and `FullAuditEntityMixin` inside `mixins.py` to allow rapid onboarding of new entities with a single inheritance line.
3. **Sort Order Enforcement**: SQLAlchemy 2.0 `mapped_column(sort_order=X)` was heavily utilized. UUID is forced to `-100` (always first), while audit metadata is forced to `900+` (always at the bottom of the table schema). This creates highly readable database schemas natively.
4. **Optimistic Locking**: Handled elegantly via SQLAlchemy's `version_id_col` mapper argument in `VersioningMixin`. If two parallel processes attempt to update the same record simultaneously, the second one will raise a `StaleDataError`, preventing race conditions natively in the ORM.
5. **Generic Serialization**: `BaseEntity` provides generic `to_dict()` and `to_json()` methods. While DTO mapping via Pydantic will handle API serialization, these generic methods are crucial for backend debugging and message queue serialization.

## Known Limitations
- The `AuditMixin` (who created/updated the row) currently uses string placeholders (`DatabaseTypes.STRING_MEDIUM`). This expects either a User UUID string or a System Identifier string, as we do not yet have a User table to establish Foreign Keys against.

## Future Improvements
- **Repository Integration**: In upcoming Sprint tasks, the abstract base repository will automatically hook into `soft_delete()` and `restore()` methods from the `SoftDeleteMixin` so that generic `.delete(id)` calls automatically route to soft deletion.
