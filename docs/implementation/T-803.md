# T-803: Enterprise API Client & Network Integration

## Executive Summary
This document outlines the successful implementation of the Enterprise API Client and Network Integration layer for the Flood Guardian Flutter application (Sprint 8, Task T-803). The network layer provides a centralized, robust, and testable abstraction between Flutter features and the backend API, effectively isolating UI from HTTP logic.

## Existing API Contract
The implementation strictly adheres to the Sprint 7 backend API contract:
- **Base URL**: Environment-aware via `AppConfig`.
- **Success Response**: Enveloped with `data`, `meta`, `request_id`, `timestamp`, and `version`.
- **Error Response**: Enveloped with `error_code`, `message`, `details`, `request_id`, `timestamp`, `path`, and `version`.
- **Pagination**: Supports standard `page`, `page_size`, `total`, `total_pages`, `has_next`, and `has_previous` metadata.

## Network Architecture
The core abstraction relies on the `ApiClient` interface, implemented via `DioApiClient`. `Dio` was chosen as the HTTP client (already present in `pubspec.yaml`) as it is lightweight and extensible via Interceptors. 

### ApiClient
`DioApiClient` provides generic support for standard HTTP methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`). It handles Base URL initialization and configuration of standard headers and timeouts centrally.

### Request Pipeline
Requests are pre-processed by a series of interceptors:
1. **TracingInterceptor**: Automatically injects UUIDs for `X-Request-ID` and `X-Correlation-ID`.
2. **AuthInterceptor**: Injects the `Authorization: Bearer <token>` header, sourced from an abstract `TokenProvider`.
3. **LoggingInterceptor**: Safely logs request metadata (Method, URI, Request ID) without exposing sensitive bodies.

### Response Pipeline
Responses are processed through models specifically mapped to the Sprint 7 contract:
- `SuccessResponse<T>` for standard responses.
- `PaginatedResponse<T>` for list endpoints containing pagination metadata.

### Error Mapping
`DioException`s are captured and mapped into safe, application-level `NetworkException` subclasses:
- `TimeoutException`, `NoInternetException`, `RateLimitException`, `ServerException`, `ValidationException`, `UnauthorizedException`, `ConflictException`, and `NotFoundException`.
These are further converted into standard `AppFailure` types within the repositories to isolate the presentation layer from network internals.

### Retry Policy
A smart `RetryInterceptor` is implemented with the following behavior:
- Automatically retries idempotent operations (`GET`, `PUT`, `DELETE`).
- Triggers on connection timeouts, receive timeouts, or 502/503/504 server errors.
- Avoids retrying non-idempotent operations (e.g. `POST`) unless explicitly flagged as `allowRetry = true` to prevent duplicate operations.
- Employs exponential backoff with a maximum of 3 retries.

### Rate Limit Handling
The `RateLimitInterceptor` intercepts 429 status codes. It parses the `Retry-After` header and throws a `RateLimitException` carrying the duration. The system handles 429 safely by deferring to the caller rather than causing retry storms.

### Repository Boundary
Remote data source interfaces (`AreaRemoteDataSource`, `PredictionRemoteDataSource`, `AlertRemoteDataSource`, `NotificationRemoteDataSource`) were created mapping exactly to the backend routers `/areas`, `/predictions`, `/alerts`, and `/notifications`. The feature repositories depend exclusively on these abstractions. 

## Authentication Readiness
A `TokenProvider` interface was introduced. The `AuthInterceptor` uses it to retrieve tokens asynchronously. The actual implementation of token management, login flows, and token refresh are explicitly deferred to T-804.

## Security
- No secrets are hardcoded in the source code.
- Authorization headers and request bodies are explicitly excluded from application logs.
- Certificates are validated correctly through the default HTTPS pipeline (no insecure fallback was introduced).

## Testing Results
Unit tests were written and successfully passed for:
- Envelope parsing (`SuccessResponse`, `PaginatedResponse`, `ApiError`).
- Request/Error mapping in the interceptors.
- `flutter analyze` completed with no critical errors.
- `flutter test` executed and passed all tests.

## Build Results
`flutter build apk --debug` completes without errors, and the application is ready for integration deployment.

## Future Improvements

- **Refresh Token Mechanism**: To be implemented by T-804, seamlessly hooking into the `AuthInterceptor` or replacing it with an advanced interceptor that locks requests during refresh.
