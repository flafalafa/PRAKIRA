# T-603: Penjadwal Notifikasi Enterprise (Enterprise Notification Scheduler)

## Ringkasan
Berhasil mengimplementasikan **Enterprise Notification Scheduler**. Jika *Policy Engine* bertugas menyaring (iya/tidak), maka *Scheduler* bertugas mengatur **KAPAN** pesan itu dikirim. Modul ini adalah "Kurir Internal" yang mengantrekan pesan, memastikan pesan darurat didahulukan, dan menangani pengiriman ulang (*retry*) secara cerdas apabila API pihak ketiga (misalnya WhatsApp/Firebase) sedang *down* atau menolak koneksi.

## Keputusan Arsitektur
1. **Antrean Berbasis Prioritas (`MemoryPriorityQueue`)**: Antrean kita menggunakan sistem kasta ketat. Pesan berstatus `EMERGENCY` (Tanggul Jebol) akan otomatis "menyalip" (bypass) ratusan pesan `LOW` atau `NORMAL` yang sudah antre lebih dulu. Warga di zona kritis tidak boleh terlambat menerima pesan hanya karena server sedang sibuk mengirim notifikasi "Aman" ke daerah lain.
2. **Penundaan Cerdas (*Exponential Backoff Retry*)**: Jika pengiriman gagal (misal API Firebase *Timeout*), *Dispatcher* tidak akan membombardir ulang secara membabi buta. Ia menggunakan algoritma *Exponential Backoff*. Percobaan ulang 1 dilakukan setelah 1 menit, percobaan 2 setelah 2 menit, percobaan 3 setelah 4 menit. Ini mencegah *server* kita masuk *blacklist* (terblokir) akibat *Spamming API*.
3. **Eksekusi Tertunda (*Deferred Delivery*)**: Jika *Policy Engine* pada T-602 memvonis pesan untuk ditahan (*DEFER*) akibat hukum *Cooldown*, *Scheduler* akan menaruh pesan tersebut dalam status `WAITING` dan menjadwalkan peluncurannya tepat ketika masa tenggang (15 menit) berakhir.
4. **Pelacakan Status (*State Machine*)**: Setiap pesan dilacak siklus hidupnya. Mulai dari `QUEUED` (Antre), `RUNNING` (Sedang Dikirim), hingga `COMPLETED` (Selesai) atau `FAILED` (Gagal Permanen).

## Batasan yang Diketahui
- **In-Memory Queue**: Antrean saat ini menggunakan struktur data RAM (Memory). Jika *server backend* mati terputus aliran listrik, semua antrean yang belum terkirim akan hilang.
- `JobExecutor` saat ini masih berupa stub (simulasi) karena implementasi *channel* aslinya ada di tiket berikutnya.

## Peningkatan Kedepan
- **Distributed Queue**: Mengganti `MemoryPriorityQueue` dengan *Redis* atau *RabbitMQ* agar antrean tidak hilang (*persistent*) saat server *restart*, dan memungkinkan ratusan mesin server pekerja (*worker nodes*) memproses antrean secara bersamaan jika skalanya membesar mencakup seluruh Indonesia.
