# T-402: Pengumpul Data Cuaca BMKG (BMKG Weather Collector)

## Ringkasan
Berhasil mengimplementasikan Modul Kolektor (Pengumpul Data) untuk BMKG dengan sepenuhnya mewarisi dan mematuhi arsitektur *Enterprise Collector Foundation* (T-401). Kolektor ini dirancang khusus untuk menyedot, membedah, dan menormalisasi rilis prakiraan cuaca terbuka dari BMKG (format XML) dan menyulapnya menjadi struktur data standar (Canonical DTO) yang siap dikonsumsi oleh lapisan *Domain* Flood Guardian nantinya.

## Keputusan Arsitektur
1. **Asynchronous HTTP Client (`httpx`)**: Karena proses menarik data dari pihak luar (Apalagi ke server pemerintah yang mungkin padat trafik) rawan terhadap *blocking* / kemacetan, klien HTTP dibangun murni secara *asynchronous* (`async/await`) menggunakan modul `httpx`.
2. **Isolasi Kegagalan (Failure Isolation via Backoff)**: Sistem diatur untuk tidak serta-merta menyerah (crash) jika BMKG *timeout* atau mengembalikan *Error 500*. Kolektor ini dilengkapi mekanisme *retry* dengan pola *delay* (Backoff) untuk memastikan ketahanan jaringan.
3. **Pemisahan Tanggung Jawab Secara Brutal (*Strict Single Responsibility*)**:
    - **`client.py`**: Hanya mengurusi jaringan. Buta sama sekali terhadap format XML.
    - **`parser.py`**: Hanya membaca XML dan merakitnya menjadi kamus (dictionary) Python. Tidak tahu urusan jaringan.
    - **`normalizer.py`**: Mengubah kamus (dictionary) Python menjadi cetakan standar *Flood Guardian* (`NormalizedData`).
    - **`validator.py`**: Memverifikasi bahwa cetakan standar tersebut tidak kopong/kosong.
    - **`mapper.py`**: Bersiap mencetak resep untuk dikirim ke Lapisan Bisnis Domain kelak.
4. **Pendaftaran Otomatis (Auto-Registration)**: Saat file `collector.py` BMKG di-impor, ia secara pintar akan langsung mendaftarkan dirinya ke `CollectorRegistry` sebagai penyedia bernama `"BMKG"`. Sistem *Factory* nantinya bisa langsung memanggil kolektor ini dari mana saja.

## Siklus Request & Normalisasi (Request Lifecycle)
1. **Connect**: Klien *httpx async* dibuka.
2. **Fetch XML**: Permintaan dikirim ke `data.bmkg.go.id/DataMKG/MEWS/DigitalForecast`. XML Mentah diraih sebagai `RawPayload`.
3. **Parse**: Modul pembelah XML (`xml.etree.ElementTree`) membaca struktur berjenjang (*nested*) BMKG yang khas (`forecast -> area -> parameter -> timerange -> value`). 
4. **Normalize**: Parameter-parameter kriptik BMKG seperti `hu` (Humidity), `t` (Temperature), dan format waktu aneh (`202410211200`) dikonversi secara damai menjadi zona waktu *UTC datetime* yang modern dan disuntikkan ke dalam `NormalizedData.time_series`.

## Batasan yang Diketahui
- Kolektor ini tidak menyimpan (*persist*) data ke *Database* dan **tidak** memanggil entitas Domain (`WeatherObservation` atau `RainfallEntity`) secara langsung. Aturan T-402 secara eksplisit melarang penyatuan ini. Kelak di Sprint 5, Layanan Aplikasi (*Application Services*) lah yang bertugas mencaplok hasil dari Kolektor ini dan mendistribusikannya ke Entitas.

## Peningkatan Kedepan
- **Polling Otomatis (Scheduler)**: Kolektor ini masih pasif dan harus dipicu (*triggered*). Di masa depan, integrasi dengan *Celery* atau *APScheduler* diperlukan untuk membuatnya bangun setiap 6 jam sekali secara mandiri, mengambil data terbaru BMKG, dan memicu kalkulasi ulang risiko banjir di daerah-daerah bantaran sungai yang dituju.
