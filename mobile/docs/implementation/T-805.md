# Enterprise Location & Area Module
# ==========================================

STATUS: READY_FOR_REVIEW

## Executive Summary
Task T-805 establishes the foundational module for Location and Area in the Flood Guardian mobile application. This implementation adheres strictly to the Sprint 7 Backend Area API contract and does not invent any missing functionality or introduce any GPS/Maps coupling at this stage. It reuses existing networking and DI infrastructure (T-803 and T-804).

## Actual Backend Area Contract
Verified via FastAPI (`backend/app/api/v1/routers/areas.py`) and schema definitions:
- Endpoint: `GET /areas` (paginated, with filters)
- Endpoint: `GET /areas/{area_id}`
- Status Enum: Represented explicitly; unknown/future values fall back to an unknown status.
- No GPS tracking or background tracking endpoints exist or are consumed here.

## Area Model
Created `AreaModel` and `LocationModel`.
- Strongly typed.
- Supports robust JSON deserialization.
- `status` uses `AreaStatus` enum with an explicit fallback `AreaStatus.unknown` to prevent crashes when backend adds new types.
- Validates properties and drops `dynamic` quickly at the API boundary.

## Area Repository
Created `AreaRepositoryImpl` implementing `AreaRepository`.
- Connects the RemoteDataSource to the UI layers.
- Validates failure mappings from `NetworkException` to `AppFailure`.
- Manages selected Area ID persistence seamlessly.

## Area Remote Data Source
Refactored existing `AreaRemoteDataSource` (T-803) to return strongly typed `PaginatedResponse<AreaModel>` instead of `Map<String, dynamic>`.
- Reused the `ApiClient`.

## Active Area Selection & Persistence
Created `SharedPrefsAreaSelectionStorageImpl`.
- Backed by SharedPreferences (smallest appropriate storage mechanism).
- Exposes saving, loading, and clearing of a selected string ID (not a secret).

## Startup Restoration & State Management
Created `AreaController` (extends `ChangeNotifier`).
- States: `Initial`, `Loading`, `Loaded`, `Empty`, `Error`.
- Restoration is handled via `restoreActiveArea()`. If the Area is deleted or backend returns an error during restoration, the ID is safely cleared to prevent application lock.

## Authentication Integration
All requests automatically utilize the authenticated `ApiClient` and `AuthInterceptor` from T-804. No manual `Bearer` token logic was added to the Area module.

## GPS Readiness Boundary
Created `LocationProvider` interface and `NoOpLocationProviderImpl`.
- Provides an architectural placeholder for future GPS/Location services without pulling in iOS/Android native location libraries or Google Maps yet.

## UI Validation
Created `AreaSelectorWidget`.
- Uses T-802 Design System (Cards, Loading, Error State, Empty State).
- Responsive minimal interface, compliant with accessibility basics (touch targets, visible active state).

## Testing Results
- Unit tests written for `AreaModel`, `AreaRepositoryImpl`, and `AreaController`.
- 100% test passing rate (25 tests).
- `flutter analyze` passes perfectly (No issues found).

## Regressions
- **T-803 Regression**: None. `ApiClient` remains unchanged and continues to handle pagination securely.
- **T-804 Regression**: None. `SessionManager` and DI `ServiceLocator` remain the source of truth.

## Build Results
- Similar to T-804, a local `flutter build apk` fails purely due to the local environment lacking a full Java SDK in this workspace. Code integrity is verified through flutter test and static analysis.

## Known Limitations & Future Improvements
- No offline caching exists yet for Area metadata (only the selected ID is persisted locally).
- GPS will require actual location plugins (`geolocator` or similar) later.
- Maps require a dashboard task.
